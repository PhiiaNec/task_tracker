# Вопросы

## 1. Какой Linux-дистрибутив и версия используются на сервере?

Это определяет совместимость трекера, способ установки зависимостей, особенности безопасности и порядок обновления системы в условиях отсутствия интернета.

* **Debian / Ubuntu LTS** ➡️ Буду выбирать среди Redmine, OpenProject, Plane, Wekan, Kanboard, Vikunja, Planka и Taiga, т.к. все они имеют варианты контейнерного развёртывания. Проверю совместимость Docker Engine с ОС, доступность необходимых образов и возможность их офлайн-переноса. Для офлайн-доставки системных пакетов использую apt-offline, проверю совместимость Docker с AppArmor и доступом к томам. Это выглядит как наиболее предпочтительный вариант благодаря большому количеству документации и длительной поддержке версий.
* **RHEL** ➡️ Рассмотрю те же трекеры, но проверю совместимость развёртывания Docker с SELinux в режиме Enforcing, если он блокирует доступ контейнера к файлам или томам, настрою необходимые контексты безопасности. Для установки системных пакетов без интернета использую dnf download --resolve или локальный репозиторий. Если Docker-развёртывание окажется проблемным, рассмотрю альтернативные способы установки, например пакетную установку Redmine или Vikunja.
* **SUSE** ➡️ Рассмотрю те же трекеры, проверю доступность Docker Engine с конкретной версией SUSE и особенности работы с томами и механизмами безопасности. Если возникнут проблемы с контейнерным развёртыванием, рассмотрю пакетную установку OpenProject (SLES 15). Для офлайн-установки системных зависимостей рассмотрю ISO/DVD или локальный репозиторий. Гайдов меньше, поэтому нужно будет времени на инструкции.
* **Alpine** ➡️ Сначала рассмотрю Vikunja и OpenProject, т.к. оба проекта предоставляют официальные Docker-образы. Дополнительно проверю Kanboard, Redmine и Planka. Для каждого кандидата проверю наличие образов под архитектуру сервера (AMD64/ARM64), возможность офлайн-переноса и отсутствие необходимости обращаться к внешним ресурсам при запуске. musl libc может создавать проблемы при непосредственной установке приложений, но сама по себе не препятствует запуску Docker-контейнеров с собственным окружением.
* **Ещё не выбран** ➡️ Предложу Ubuntu Server 24.04 LTS как основной вариант или Rocky Linux 9 как альтернативу, это позволит выбирать трекер из широкого набора решений без существенных ограничений по способу развёртывания.

**Осознанно исключены:** Arch Linux, Tumbleweed, не LTS версии (rolling release, короткий срок/нет формального срока поддержки, частичное обновление невозможно - высокий риск для air-gap)

## 2. Какова ожидаемая нагрузка - сколько задач в месяц?

- **До 100** ➡️ Буду сравнивать по простоте настройки, удобству интерфейса. В первую очередь рассмотрю Vikunja, Kanboard, Wekan и Planka. Redmine и OpenProject тоже оставлю кандидатами, если потребуется более сложное управление проектами, но буду учитывать дополнительные затраты на настройку.
- **До 1000 ➡️** Помимо удобства проверю поиск, фильтрацию, сортировку, историю изменений и возможности отчётов. Рассмотрю все 8 трекеров: Redmine, OpenProject, Plane, Vikunja, Taiga, Kanboard, Wekan и Planka.
- **Более 1000** ➡️ Выделю производительность и возможности масштабирования в отдельные критерии. В первую очередь рассмотрю Redmine, OpenProject, Plane, Vikunja. Посмотрю, насколько остальные кандидаты подходят для работы с большим количеством задач.
- **Нагрузка неопределенна ➡️** Учту возможность увеличения нагрузки на будущее. Сравню Redmine, OpenProject, Plane и Vikunja по возможностям расширения, настройке фильтров и работе с большими списками задач. Предпочту решение, которое не потребует смены платформы при увеличении нагрузки. При этом учту, что для команды из 5–10 человек избыточно сложная система может оказаться неудобнее более простого решения

**Заведомо исключены из сравнения:** YouTrack из-за проприетарности, Focalboard из-за заброшенности проекта.

## 3. Предполагаются ли доработки трекера сверх стандартных настроек? Если да, есть ли специалист, который сможет их выполнить?

- **Доработки не предполагаются, достаточно стандартных возможностей** ➡️ Сравню трекеры по готовности к использованию после установки и настройки. Основное внимание уделю возможностям, доступным без программирования. В первую очередь рассмотрю Vikunja, Kanboard, Wekan и Planka. Redmine и OpenProject также оставлю кандидатами, если их дополнительные возможности окажутся полезны, но может потребоваться доп настройка и подключение плагинов.
- **Доработки возможны, есть внутренний разработчик или подрядчик** ➡️ Помимо стандартных возможностей проверю наличие плагинов, открытого API и документации для разработчиков. В первую очередь рассмотрю Redmine, OpenProject и Plane: их возможности расширения могут быть полезны при адаптации системы под специфические требования. Также проверю, какие возможности для доработки предоставляют Vikunja и Kanboard.
- **Доработки могут понадобиться, но исполнителя пока нет** ➡️ Отдам предпочтение трекерам, которые закрывают основные потребности стандартными средствами, но при этом допускают дальнейшее расширение: Vikunja, Kanboard и Planka как варианты с готовой Kanban-функциональностью и Redmine благодаря возможностям расширения через плагины и API (их использование может потребовать привлечения специалиста).

## 4. Какие способы интеграции с системой поддержки доступны?

Нужно выяснить, предоставляет ли система поддержки REST API, поддерживает ли вебхуки, а если API отсутствует, есть ли возможность экспорта данных или доступа к базе.

- **Есть REST API, достаточно создавать задачи из обращений** ➡️ Выбираю Redmine, Vikunja или Kanboard. Для интеграции достаточно возможностей API обеих систем; при сравнении учту простоту настройки обмена данными.
- **Есть REST API, нужно отслеживать изменения в обращениях** ➡️ Если система поддержки поддерживает вебхуки, рассмотрю Redmine, Vikunja, Taiga. Если вебхуков нет, но API позволяет получать актуальные данные, можно использовать периодический опрос (polling).
- **Нет API, есть экспорт обращений или доступ к базе данных** ➡️ Redmine, Vikunja и Kanboard. Можно будет организовать ручной перенос данных или подготовить промежуточный скрипт для автоматического создания задач. Возможность автоматизации будет зависеть от формата экспорта или доступности и структуры базы данных.

## 5. Есть ли у организации дополнительные требования к безопасности и используемому ПО?

- **Особых требований нет, достаточно стандартных настроек безопасности** ➡️ Сравню возможности разграничения прав доступа, настройки ролей и ведения журнала действий. Предпочту трекер, в котором необходимые настройки доступны без дополнительных доработок.
- **Есть внутренние требования к безопасности или используемому ПО** ➡️ Нужно иметь ввиду, какие именно требования обязательны: использование ПО из российского Реестрач, наличие сертификатов или соответствие определённым стандартам. Проверю, какие из рассматриваемых решений им соответствуют.
- **Требования пока неизвестны** ➡️ Буду исходить из того, что для организации важны базовые меры безопасности и возможность разграничения прав доступа. При сравнении учту наличие журналирования действий, защищённого соединения и возможность дальнейшего усиления безопасности за счёт дополнительных настроек и плагинов. Наличие в Реестре российского ПО также учту как дополнительное преимущество.

## 6. Какие способы получения уведомлений нужны пользователям?

Нужно уточнить, достаточно ли уведомлений внутри трекера или требуется отправлять их по электронной почте, либо в корпоративный мессенджер. Также важно понять, нужны ли автоматические напоминания о просроченных задачах.

- **Достаточно уведомлений внутри трекера (in-app)** ➡️ Рассмотрю всех основных кандидатов, сравню встроенные возможности уведомлений. Дополнительные почтовые серверы и интеграции не потребуются.
- **Нужны уведомления по электронной почте (SMTP)** ➡️ Поищу возможности настройки SMTP и отправки уведомлений о назначении задач, изменении статусов и сроках выполнения. Поскольку система должна работать без интернета, потребуется внутренний почтовый сервер.
- **Нужны уведомления в мессенджере** ➡️ Уточню, какой мессенджер используется. Для Mattermost рассмотрю возможность интеграции через API и вебхуки. Для МАКС проверю наличие готовых способов интеграции или возможность разработки собственного решения. Также учту, что обмен уведомлениями должен работать внутри закрытой сети.
- **Нужны автоматические напоминания о просроченных задачах** ➡️ Дополнительно сравню возможности настройки уведомлений по расписанию. Учту, доступны ли они стандартными средствами или потребуют скриптов.

## 7. Нужна ли возможность прикреплять файлы к задачам и какого размера?

- **Вложения нужны, файлы могут быть большими** ➡️ Сравню максимальный размер одного файла, возможности настройки лимитов и хранения вложений. Также учту, как файлы включаются в резервное копирование.
- **Вложения нужны, но файлы небольшие** ➡️ Проверю наличие встроенной возможности прикрепления файлов и стандартные ограничения на их размер. Если лимиты можно настраивать, учту это как преимущество.
- **Вложения не нужны** ➡️ Не буду учитывать работу с файлами как критерий при сравнении трекеров.
