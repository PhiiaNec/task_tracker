## Какие Linux-сервера стоит использовать для работы без интернета (вопрос 1)?

В случае, если сервер имеет доступ в интернет, особой разницы нет, т.к. мы можем использовать apt/dnf install *имя пакета* и все необходимые зависимости подтянутся из сети.

В случае офлайн-доступа имеют смысл различия в особенностях архитектуры. Это важно для понимания того, какие пакеты потом придётся скачивать, потому как пакет для одного дистрибутива чаще всего не подойдёт для другого. Также разные дистрибутивы используют разные системы безопасности и имеют разный статус поддержки версий - нужен живой и свежий вариант. + Разное количество предустановленного софта, что может быть как плюсом, так и минусом в зависимости от ситуации.

### Где больше предустановленного софта (условно, а не строго)?

В любом из дистрибутивов можно сместить акцент в более лёгкую или нагруженную сторону.

- **Debian** - минималистичный, чистая база (~300 МБ)
- **Ubuntu** - средний вариант
- **RHEL** - тяжелее всех, наиболее безопасный, предсказуемый вариант (~2 ГБ)
- **openSUSE Leap** -  ближе к среднему (AppArmor, меньше фоновых сервисов, чем в RHEL)
- **SLES** - тяжелее и ближе к RHEL по корпоративной нагруженности
- **Tumbleweed** - переменная величина, зависит от установленного набора
- **Alpine Linux** - самый лёгкий из списка (~5–10 МБ ), всё ставится по необходимости, ориентирован на контейнеры и минимальную поверхность атаки

## Какие системы поддержки бывают и как они связаны с API? (вопрос 4)

**Система поддержки (helpdesk)** - программа, в которой сотрудники компании ведут обращения пользователей: фиксируют проблему, отвечают, переводят в статусы и закрывают.

**Упрощённо состоит из следующих элементов:**

* **Обращение** (тикет)  - карточка с текстом проблемы, уникальным номером, автором, датой, вложениями и историей переписки
* **Статусы** отражают текущее положение обращения в процессе решения (например, Новый -> В работе -> Ожидает ответа -> Решен ->  Закрыт)
* **Очереди** группируют обращения по теме, статусу, исполгитедю и/или приоритету
* **Роли** - кто отвечает (агент), смотрит (наблюдатель), управляет (руководитель поддержки), также есть администратор
* **Каналы** - откуда приходит обращение (почта, форма на сайте, чат, телефон)

### Системы поддержки по моделям развёртывания

Именно модель развёртывания определяет системные API и вебхуки:

- **Облачные (SaaS)**: работают только у вендора, в закрытый контур их не поставить. Обычно богатый REST API и вебхуки, но для air-gap не подходят, т.к. данные хранятся вне внутреннего контура, а без интернета система недоступна.
- **Локальные (On-premise):** устанавливаются на собственных серверах компании и работают без интернета. Организация самостоятельно отвечает за инфраструктуру, обслуживание и обновление.
- **Гибридные (Hybrid):** сочетают локальную инфраструктуру с облачными сервисами. Часть данных и компонентов системы хранится внутри компании, а остальные используются через облако.
- **Частные облачные (Private Cloud):** размещаются в выделенной облачной инфраструктуре, предназначенной для одной организации. Обеспечивают больший контроль над средой и данными по сравнению с публичным облаком.

### API

**API** (Application Programming Interface) - это программный интерфейс, который позволяет разным приложениям обмениваться данными и использовать функции друг друга, набор правил и методов, с помощью которых одно приложение может запросить информацию или действие у другого.

**Принцип:** Похоже на меню в ресторане. Клиент смотрит в меню и заказывает блюдо, а кухня (сервер) его готовит и приносит. Клиенту не нужно знать, как именно устроена внутренняя логика сервера, на каком языке он написан и как организована его база данных. API скрывает сложность реализации (инкапсулирует её), предоставляя наружу только стандартизированный набор методов.

Например, приложение погоды на телефоне отправляет запрос к API метеослужбы, получает данные о температуре и показывает их вам.

 **Подхода к обмену данными:**

- **REST** (классический архитектурный подход): взаимодействие между системами происходит посредством HTTP-запросов:

  - GET (получить данные)
  - POST (создать запись)
  - PUT/PATCH (обновить данные)
  - DELETE (удалить запись).

    REST API позволяет самостоятельно запрашивать и изменять данные.
- **Вебхуки** (событийный подход): автоматическая передача данных в другую систему при наступлении определённого события

  **Принцип:** Похоже на SMS-уведомление от банка или звонок в дверь. Вы не стоите у двери и не спрашиваете каждую секунду «кто там?», курьер 				сам звонит, когда приходит.

  Например, клиент оплатил покупку в интернет-магазине, платёжная система мгновенно отправляет POST-запрос на сервер магазина со статусом «оплачено».

При этом REST и вебхуки не являются взаимоисключающими технологиями.

### Связь систем поддержки с API:

Модель развёртывания не определяет наличие API и вебхуков напрямую, но влияет на доступность этих механизмов, условия их настройки и интеграции с другими системами.

REST API позволяет внешней системе получить список обращений из helpdesk или создать новое обращение. Вебхуки, напротив, автоматически передают информацию о событиях: например, уведомляют CRM о создании нового тикета или изменении его статуса.

**Модель развёртывания влияет на условия интеграции:**

* **SaaS:** интеграция обычно выполняется через доступные API и вебхуки поставщика. Необходим доступ к интернету.
* **On-premise:** API и вебхуки могут использоваться для интеграции с внутренними системами без передачи данных во внешнее облако.
* **Hybrid и Private Cloud:** позволяют сочетать внутренние и облачные интеграции в зависимости от архитектуры и настроек доступа.

### SMTP - внешняя почта

**SMTP** (Simple Mail Transfer Protocol) - это протокол отправки  **электронной почты** . Когда трекер «уведомляет через SMTP», он **отправляет письмо** на почтовый адрес пользователя.

* **Где появляется уведомление:** в почтовом ящике (Outlook, Thunderbird, веб-почта).
* **Что нужно для работы:** настроенный **почтовый сервер** (SMTP-сервер). В air-gap это **внутренний** почтовый сервер компании - внешний (Gmail, Mail.ru) недоступен.
* **Плюсы:** письмо можно прочитать с телефона, оно сохраняется в архиве, работает привычно.
* **Минусы:** в закрытом контуре нужно поднимать и обслуживать SMTP-сервер; письма могут попадать в спам; задержка доставки.

### In-app - внутри самого приложения (трекера в данном случае)

**In-app** (in-application) - уведомление, которое появляется  **внутри самого трекера** : колокольчик в углу интерфейса, всплывающее окно, счётчик непрочитанных, лента событий.

* **Где появляется уведомление:** в веб-интерфейсе трекера, когда пользователь в него зашёл.
* **Что нужно для работы:**  это встроенная функция трекера
* **Плюсы:** не требует почтового сервера, мгновенно, не зависит от внешних сервисов -  **идеально для air-gap** .
* **Минусы:** пользователь увидит уведомление,  **только когда откроет трекер** . Если он в трекер не заходит - он не узнает о задаче.

### Мессенджеры

**Mattermost** - это корпоративный мессенджер с открытым исходным кодом, который является одним из главных конкурентов Slack и Microsoft Teams. Его ключевая особенность для вашей задачи - возможность  **полностью развернуть на собственном сервере (on-premise)** . Это означает, что все данные и переписка остаются внутри вашей инфраструктуры, что идеально вписывается в требование работы без доступа в интернет.

С точки зрения интеграции с трекером, Mattermost - это «продвинутый» инструмент. У него есть **полноценный REST API** и система вебхуков, что позволяет создавать сложные сценарии автоматизации и уведомлений. Он хорошо интегрируется с популярными инструментами разработки, включая Jira, и для него существуют запросы на интеграцию с YouTrack. Это выбор, который часто делают DevOps-команды, готовые поддерживать собственную инфраструктуру.

## Наиболее вероятные развилки вопросов (допущения)

1. **Операционная система:** Debian-семейство. Это позволит использовать контейнерное развёртывание и не ограничивать выбор трекера конкретным дистрибутивом. При сравнении проверю возможность установки на Linux и работы без доступа к интернету.
2. **Нагрузка:** небольшая нагрузка задач до 100 в месяц, т.к. команда состоит из 5–10 человек, поэтому в первую очередь буду учитывать простоту настройки и удобство интерфейса при этом не стану полностью игнорировать возможности поиска и фильтрации.
3. **Доработки:** на начальном этапе будет достаточно стандартных возможностей трекера. Однако возможность дальнейшего расширения через плагины и API кважна.
4. **Интеграция с системой поддержки:** предполагаю наличие REST API и необходимость создавать задачи на основании обращений. Пока вероятно будет достаточгно автоматического создания задач, поэтому отдельно оценю наличие и удобство API у Redmine, Vikunja и Kanboard.
5. **Безопасность:** предположительно нужны базовые меры безопасности (из-за итак планируемой закрытости трекера), разграничение прав доступа, но также перспектива развития этой системы в случае чего. При сравнении учту наличие журналирования действий, защищённого соединения и возможность дальнейшего усиления.
6. **Уведомления:** встроенные уведомления + внутренняя почта. Возможность интеграции с корпоративным мессенджером и настройки автоматических напоминаний рассмотрю как дополнительные преимущества, но не стану брать как основной критерий.
7. **Вложения:** наиболее вероятно нужны. Сравню стандартные ограничения на размер файлов, возможность изменения лимитов и особенности хранения.

Таким образом, основное внимание при сравнении будет уделено тому, насколько Redmine, Vikunja и Kanboard подходят для небольшой команды, работающей по Kanban, и насколько легко их можно развернуть и настроить в закрытом контуре. Дополнительные возможности буду учитывать как преимущества, если они не требуют чрезмерных затрат на настройку и сопровождение.

## Обоснование выбора

Формулировки критериев и их [объяснения](#объяснение-критериев-для-себя-чтобы-не-забывать-и-не-путаться) хранятся в разделе хода работы.

В [comparison_table.md](comparison_table.md) я коротко описала, какому трекеру отдаётся предпочтение по каждому критерию, но это стоит воспринимать как промежуточный результат сравнения, нужный для понимания сильных и слабых сторон каждого варианта, а не как окончательный рейтинг. Здесь нужно исходить из того, какие цели важнее для поставленной задачи, да и критерии не равнозначны между собой.

|                    | Аргумент в пользу выбора                                                                 | Что вызывает вопросы                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Redmine**  | Гибкие роли и права, REST API, развитые возможности расширения   | Для Kanban нужен плагин; настройка сложнее                                                 |
| **Vikunja**  | Встроенный Kanban, простое развёртывание, удобные уведомления | Нельзя гибко разделить права руководителя и исполнителя                 |
| **Kanboard** | Встроенный Kanban, специализированные роли и поиск                      | API использует JSON-RPC, возможности за пределами Kanban более ограничены |

Несмотря на количественный недостаток (2 против 4 у Redmine и Vikunja) в поинтах по критериям из таблицы, по итогу я склоняюсь к **Kanboard**. Основным аргументом стала степень соответствия функциональным требованиям ТЗ. Kanboard представляет собой специализированный Kanban-трекер со встроенной доской и возможностью настройки колонок.

Система поддерживает стандартные и пользовательские роли, что позволяет организовать разграничение прав между руководителем, исполнителем и наблюдателем, для последующей интеграции с существующей системой поддержки Kanboard предоставляет JSON-RPC API, позволяющий выполнять операции с задачами и проектами. Несмотря на отличие используемого протокола от REST API, это не исключает возможность реализации необходимого взаимодействия, хотя возможно с REST API было бы несколько проще. Тут дело в большей сбалансированности остальных преимуществ: по сравнению с Redmine, Kanboard не требует установки дополнительного плагина для организации Kanban-доски, а по сравнению с Vikunja предоставляет более гибкие возможности настройки пользовательских ролей, что делает его более лёгким в перспективе эксплуатации (мы всё ещё не знаем, есть ли в распоряжении профильный специалист для обслуживания).

Ограниченная функциональность за пределами Kanban также не является существенным недостатком для небольшой команды с заданным форматом работы. Таким образом, Kanboard выбран как решение, наиболее соответствующее текущим функциональным требованиям и не требующее дополнительных компонентов для реализации основного рабочего процесса. Текущий выбор -  не доказательство превосходства Kanboard по всем параметрам. В частности, я не могу утверждать, что его API полностью покроет будущую интеграцию, пока неизвестны конкретные сценарии обмена данными. Однако из имеющейся информации не следует, что это помешает выбрать и развернуть Kanboard на данный момент.

# Заметки по ходу

## Как я решила, что это Kanban

Требования ТЗ задают каркас канбан-доски. Поэтому я взяла эту идею как данность. Вот почему:

- **Статусы:** «Новая - В работе - На проверке - Готово». Это стандартная схема колонок канбан-доски, соответствующая этапам workflow, где задачи перемещается между ними по мере работы.
- **Карточки:** Требуется 5 примеров задач с ролями руководителя, исполнителя и наблюдателя. В канбан-доске каждая задача - это карточка, которая содержит ответственного, статус и другую необходимую информацию.
- **Цель \- визуализация рабочего процесса:** Канбан-доска определяется как визуальный инструмент для отображения задач на разных этапах работы. Необходимость видеть задачи в определённых статусах и работать с ними за разные роли по сути и есть запрос на такую визуализацию.

## Предварительный выбор трекеров

Теперь посмотрим, какие из представленных в обзоре трекеров соответствуют изначальным требования ТЗ. Это нужно, чтобы не включать в таблицу критерии, не относящиеся к развилкам вопросов. Живые проекты с активным стабильным русскоязычным сообществом следующие (и как у них обстоят дела с ролями):

* **Redmine:** есть русская локализация, развитое сообщество, настраиваемые роли и права доступа. Для Kanban может потребоваться дополнительная настройка.
* **Vikunja:** активно развивается, имеет уровни доступа к проектам. Нужно дополнительно проверить, насколько гибко можно настроить права для трёх предусмотренных ролей.
* **Kanboard:** специализированный Kanban-трекер. Проект находится преимущественно в режиме поддержки, но исправления ошибок продолжаются. Роли предусмотрены, однако возможности их настройки ограничены.
* **OpenProject:** функционально мощная система с гибкой настройкой ролей и прав. Однако для текущей задачи её возможности могут оказаться избыточными, а развёртывание и настройка - более трудоёмкими.

В качестве трёх претендентов для сравнительной таблицы выберу Redmine, Vikunja и Kanboard. OpenProject пока исключу из-за избыточности относительно поставленной задачи.

## Объяснение критериев для себя (чтобы не забывать и не путаться)

* **Поддержка Kanban**: Настройка колонок и статусов, перемещение карточек, гибкость рабочего процесса.
* **Роли и разграничение прав** : Возможность создать роли руководителя, исполнителя и наблюдателя, настроить доступные им права.
* **Удобство настройки и использования** : Сложность первоначальной настройки, необходимость дополнительных плагинов, понятность интерфейса.
* **Поиск и фильтрация** : Возможности поиска, фильтрации и сортировки при увеличении количества задач.
* **Расширяемость** : Наличие плагинов, API и хорошей документации, возможность дальнейшей адаптации системы.
* **Возможности интеграции** : Наличие API для создания задач из обращений, возможность автоматического создания и изменения задач внешними системами.
* **Безопасность** : Разграничение прав, журналирование действий, поддержка защищённого соединения, возможность дополнительного усиления защиты.
* **Уведомления** : Встроенные уведомления, поддержка SMTP. Как +: возможность интеграции с корпоративными мессенджерами и настройки автоматических напоминаний.
* **Вложения** : Возможность прикрепления файлов, максимальный размер вложения, настройка лимитов и особенности хранения файлов.
* **Ресурсоёмкость и сопровождение** : Рекомендуемые требования к оперативной памяти и серверу, сложность обновления, резервного копирования, дальнейшего администрирования.

## Трудности

В начале работы я слишком подробно сосредоточилась на изучении недостающих для себя знаний и подготовке соответствующего конспекта. В результате на этот этап ушло больше времени, чем я изначально планировала. Последующие задачи, связанные с подготовкой итоговых материалов и оформлением результатов, пришлось выполнять в условиях ограниченного времени. Из-за этого я не успела уточнить некоторые вопросы, которые могли бы повлиять на выбор трекера и планирование его дальнейшего развёртывания. В частности, мне не удалось узнать, предусмотрен ли специалист, ответственный за обслуживание системы, а также какое API использует система поддержки.

Отдельная трудность возникла при работе с таблицей сравнения: файл с уже подготовленными данными по неизвестной причине оказался пустым, хотя до этого я сохраняла изменения. Восстановить предыдущую версию не удалось ни через историю изменений, ни из резервных копий. В результате таблицу пришлось восстанавливать практически заново, что дополнительно сократило время, доступное для выполнения остальных этапов.

К шагам 3 и 4 я приступить не успела, в том числе не удалось подготовить подробный план их выполнения. Эти этапы потребовали бы от меня предварительного изучения новых инструментов и технологий: ранее я не занималась самостоятельным развёртыванием подобных систем и практически не работала с Docker. Поэтому сначала мне пришлось бы разобраться с основами контейнеризации и способами развёртывания выбранного трекера, а уже затем переходить к установке, настройке проекта, ролей и тестовых задач. В рамках задания мне удалось выполнить подготовительную работу, сформировать вопросы с вариантами решений, сравнить несколько трекеров и обосновать предварительный выбор. Практическое развёртывание и проверка системы в работе остались за пределами выполненной части задания.
